# Chart additions: settings, selection, and tracing

Status: recommendation for review, 2026-09-23. This extends the [analytical chart coverage plan](implementation-plan.md). It does not approve every proposed chart for implementation.

## Decision frame

The user goal is to answer the next useful data question in the workspace. The proposals come from the [chart review](../pro-reviews-2026-09-21/raw/chart-review/exploreda-chart-interaction-review/review.md) and Byron's [chart-spec notes](../../transcripts/2026-08-04-chart-specs-grouping-and-derived-layers.txt) and [advanced-chart notes](../../transcripts/2026-08-04-advanced-chart-specs-and-transforms.txt). The notes are design exploration, not fixed requirements. They stress group scope, facet-local calculations, stack positions, and a route from a mark back to its inputs.

The current checkout has 11 registered panel types. Histogram is a bar mode. Violin and beeswarm are box-plot overlays. Lines connect existing numeric columns. A named grouped summary supports one group field and count, sum, or average. Pivot has its own richer reducer list. A categorical heatmap, calendar rollup, and metric card are not registered. Scatter has a point-level trace; bar planning and tracing are in active local edits. The old review describes commit `593ca2e`, so its code claims are evidence of that snapshot, not a certificate of the current working tree. Existing user edits in this checkout must remain intact.

Three paths can cover the proposals:

| Approach | Direct answers to common questions | Exact mark-to-row explanation | Settings stay coherent across views | Main limit |
| --- | ---: | ---: | ---: | --- |
| Add independent chart types with local settings and reducers | 7/10: many names appear quickly | 3/10: each renderer must rebuild membership | 3/10: metric and filter meaning diverge | Fast gallery growth hides inconsistent analysis. |
| Build one general chart grammar and query graph first | 8/10: broad expression is possible | 8/10: a full graph could retain lineage | 5/10: users must configure many concepts for simple views | The abstraction has no second proven chart contract yet. |

Keep chart-specific planning for marks and guides. The strongest simpler counterproposal is to add only creation presets and repair the grouped bar. That is the correct first proof, but it cannot answer the two-category or calendar questions.

## A settings and trace contract that can grow by example

Keep the existing chart settings object and chart registry. A new chart or mode should expose a short **Data** path: source field or fields, metric, optional group or series field, then its essential display choice. Use the existing **Facets**, **Axes**, **Select**, and **Labels** tabs only where they have real controls. Place rare calculation controls in a short, chart-specific section below the primary fields. Update valid edits immediately and keep Reset for the edit session, as [UI defaults](../../ui-defaults.md) specifies. A preset may create a familiar initial settings object without adding a new saved `type`; that is best for histogram and distribution modes. A view with a different data question and interaction model merits a new `type`; heatmap and metric card qualify.

Every derived mark should make four populations available to inspection: the source rows in the chart scope; the rows in the mark's category, pair, time bucket, or numeric bin; rows included in its numeric calculation; and rows excluded from that calculation with reasons. This distinction matters for a sum with a missing amount: the order belongs to the region even though it contributes no amount. Store source IDs with the result and keep raw and prepared values where a field conversion changed them. Show the operation, field, group keys, scope, calculated value, and drawing inputs. Preserve a stable mark identity from the saved settings and group keys. Do not use a pixel location, displayed rank, or an `Other` label as the persistent identity. For a facet, apply facet membership before a facet-local reducer; identify any global reference result separately. The scatter trace provides a useful pattern, not a requirement to make every renderer use its entire plan structure.

**Selection is a different action from inspection.** A normal click or keyboard activation on a selectable mark should apply its documented filter. A visible adjacent Inspect action should open contributors and calculation details. Trace inspection of guides and calculated drawing rules can use the current Alt-click pattern, but must also have a reachable keyboard path. A value filter, a date or numeric range, and an exact two-field pair each have different meanings. Do not encode a pair of cells as independent field filters: selecting `(North, Web)` and `(South, Retail)` that way would also select `(North, Retail)` and `(South, Web)`. A correlation cell and a reference rule do not have natural row-filter semantics; their primary action should inspect or navigate.

For each new family, prove a fixed example in three ways: displayed value, exact source IDs, and the linked filter result. Check a missing or invalid value and an active facet. Verify controls and inspection at 1280, 783, and 390 px, with pointer and keyboard input. This is a small contract check per new calculation, not a test matrix of every style combination.

## 1. Bars, histograms, and distribution presets

**Question.** Which categories or numeric bins contain records, and what is their count or measure? The current vertical bar already handles counts, numeric bins, and a separate named grouped summary. The row chart handles ranked category counts. The proposal to complete this family should start by making those paths agree on actions and metric meaning.

**Recommendation.** Keep `bar` and `row` as saved types for now. Expose **Histogram** as a creation preset for a numeric `bar`, and **Category count** and **Measure by category** as Data modes. Make horizontal/vertical orientation a display choice once the same prepared groups can drive both; do not clone the reducer in `RowChart`. The first proof remains one grouped measure that selects its group and offers Inspect. A chart can then add an optional series field with **Grouped** and **Stacked** layouts. Add **100% stacked** only after an explicit denominator rule. The chart review suggests a larger complete bar package, but doing all variants as one change would hide the harder selection and metric questions.

**Settings.** Required: category field or numeric bin field; metric `count`, `sum`, or `average`; measure field for the latter two. If a series field is present, default to grouped bars first. Display controls: orientation, sort by label/value, stable series order, Top N with a named Other group, and bin count or explicit bin width for histograms. Preserve a selected category when users change orientation or switch count to sum. If a numeric field turns into categories through a user type override, show the resulting mode clearly; do not silently keep numeric boundaries. Use one shared color assignment for a series across bars, legends, and facets.

**Math and trace.** A bin must expose its exact lower and upper bounds and boundary inclusion rule. D3's bin contract uses ordered thresholds and returns bin `x0`/`x1`; choose and test one last-bin policy for exact maxima ([D3 bin documentation](https://d3js.org/d3-array/bin)). For a stack, calculate segment start and end in data units, then scale both endpoints. The transcript correctly identifies why adding pixel heights fails under nonlinear scales. Record segment value, stack order, start/end, denominator if normalized, and member IDs. Mean values should be grouped or shown as separate marks; stacking means suggests a sum that does not exist. For signed sums, a later diverging stack can use separate positive and negative accumulators; Vega-Lite documents that variant ([Vega-Lite stack](https://vega.github.io/vega-lite/docs/stack.html)). Do not imply a 100% denominator when negative values are present. Other must retain its actual category members; a resize can alter presentation but must not change a saved filter.

**Choice.** A new type for each orientation or stack mode would duplicate settings and fracture saved selections. One configurable family with presets gives direct discovery and a single metric contract. Watch: current named `AggregateSpec` has one group field, while a series split needs two. Add the second grouping key only for the first actual grouped-bar proof; do not build a universal group engine in advance.

## 2. Categorical heatmap and matrix variants

**Question.** Which pair of categories has an unusual count or measure? The pivot already provides exact cells; a heatmap adds a scan-friendly color encoding and direct cell selection. Observable Plot distinguishes grouping nominal fields from binning continuous fields; the renderer shape can look alike while the calculation differs ([Plot group](https://observablehq.com/plot/transforms/group), [Plot bin](https://observablehq.com/plot/transforms/bin)).

**Recommendation.** Add one `heatmap` type for two categorical fields and one metric. Do not make it a tinted pivot table: the visual needs a color legend, stable row/column order, and a compact cell readout. Reuse pivot or grouped-result membership and reducer rules, but introduce a small two-key result only when the heatmap needs it. Start with one selected cell. A single pair can be represented by one value filter on each field because their intersection is exact. Disable multi-cell selection until filters can express a union of tuples.

**Settings.** Required: row category, column category, metric, optional measure. Controls: row/column sort, categorical limits, color domain, sequential versus diverging scale when the metric has meaningful positive and negative values, and optional cell labels. A sensible default is count with field order from current data. Show all displayed row/column combinations so **no source rows** has a distinct blank appearance. Show **zero** as a valid color value and **rows but no valid measure** as an invalid-measure state. Treat missing category values as a named category only when that follows the field's existing missing-value policy. State that limiting categories changes displayed coverage; let Inspect reveal omitted categories, rather than burying them in a misleading zero cell.

**Trace and action.** A cell trace gives the two typed keys, formatted labels, source IDs, valid measure IDs, excluded IDs, reducer, color domain, color value, row/column order, and facet scope. Normal activation selects the exact pair; Inspect opens its record list. A color legend explains thresholds and missing states. At narrow widths, scroll or page the matrix while preserving readable labels; do not shrink cells until keyboard focus becomes impractical.

**Variants.** A numeric density grid can later reuse rectangle drawing, but it needs numeric bin boundaries and often a different filter. A missingness matrix needs a field-by-record or field-by-group definition. Correlation needs paired-valid-row rules and a coefficient computation. Cohort retention needs cohort, elapsed-period, and denominator rules. None should inherit the ordinary heatmap's cell-selection promise merely because each uses rectangles.

## 3. Calendar time series, area, and rolling results

**Question.** How did a measure change by day, week, or month, possibly split by category? The existing line connects row-level numeric columns and remains useful for sequence data. A calendar series answers a different input question: many dated rows become one value per period and group. Vega-Lite treats time-unit conversion, aggregation, and stacking as distinct stages; that supports an explicit settings model rather than an implicit “date-looking x” shortcut ([time unit](https://vega.github.io/vega-lite/docs/timeunit), [transform order](https://vega.github.io/vega-lite/docs/transform.html)).

**Recommendation.** Keep raw-observation Line mode. Add an **Aggregate by time** Data mode to `line`, with a date field, day/week/month interval, metric, measure, and optional series category. Start with a named time-zone policy and week start; UTC is a defensible first default if shown plainly, but the choice must agree with the app's effective date values. A calendar interval is `[start, next start)`, not a fixed number of milliseconds; local days and months vary. Show the exact interval on hover and in Inspect. The x brush remains a source-date filter across all series. Make **zoom axis** a separate control if added later.

**Settings.** The primary panel should offer Date, Interval, Metric, Measure, Split by, and View (`line` or later `area`). Advanced controls can include missing-period treatment and a rolling window. For count and sum of events, an absent period can display zero if the user chooses complete intervals. For average of measurements, absent periods should break the line by default. Invalid dates and invalid measures need visible counts. Duplicate timestamps are expected input to a rollup; raw-observation mode needs an explicit sort and duplicate-x order. A series legend may hide a series locally; workspace filtering is a separate named action.

**Trace.** A point has bucket start/end, series key, source IDs, included/excluded numeric IDs, reducer result, time-zone/week rule, and final position. A line segment identifies both endpoint buckets and whether a gap was interpolated; if there is no bucket, default to a break. A rolling point identifies all input buckets and their underlying IDs, and states whether the window counts periods or valid observations. Facet-local series roll up only facet rows; a global reference stays global.

**Area choice.** Area fill is a display mode over the same ordered points, not a new data model. A single area needs a meaningful zero baseline. A stacked area needs aligned time buckets and additive metrics, with start/end values per series; an average should stay as lines. Observable Plot documents that area connects points in input order, so the planner must sort before drawing ([Plot area](https://observablehq.com/plot/marks/area)). Defer stacked area until the calendar result and bar stacking semantics both pass source-row checks.

## 4. Metric cards

**Question.** What is the current value after linked selections? The filtered row count already answers one narrow question. A metric card should show a named user measure, not merely repeat that status.

**Recommendation.** Add a `metric-card` type with count, sum, and average using the same population and numeric exclusion rules as grouped bars. Default to one value and a short scope line, such as “Revenue · 213 matching orders.” It has no axes or facets tab unless a concrete card comparison requires one. A card can offer **Inspect records**. A click on its single number should not change the current selection because it has no narrower mark subset.

**Settings and trace.** Data settings are operation, measure, title, and format. Keep the field's existing format as default. A card trace shows source row count, valid measure count, exclusions, operation, value, active workspace scope, and the field formatting rule. “No rows” and “rows but no valid values” must display differently. A later comparison needs a named baseline snapshot and both numerator and denominator populations. Do not add a green arrow or percent delta until the baseline is explicit. A rate requires an expression such as `sum(a)/sum(b)` with separate invalid-denominator handling; it is not a formatting mode.

## 5. Reference marks, regressions, and intervals

**Question.** Is a value above a target, and how was a derived line calculated? Byron's notes distinguish a global reference from a per-facet, per-color regression. They should not share an implicit calculation scope.

**Recommendation.** First add a constant reference line or band to one existing chart family, with an explicit axis, value(s), label, and style. This is a chart setting and overlay, not a new chart type. A constant target has no source rows; its trace names the saved value and scale mapping. Next, if observed work needs it, support a reference derived from a named field summary. Only then add regression to scatter as a chart-local layer with its own field, grouping, facet, method, and scope controls. A global/per-facet toggle must be visible; default to the displayed subset for a group trend. Do not put a general derived-data graph in front of this proof.

**Trace.** A calculated line stores the exact input IDs after filter, facet, and series split; omitted invalid pairs; method and parameters; coefficients; sample count; sampled path points; and visible domain. A confidence band stores its specific interval method and input population. Vega-Lite's error-band options illustrate why a band must say whether it is a standard deviation, standard error, interquartile range, or confidence interval ([error band](https://vega.github.io/vega-lite/docs/errorband.html)). Inspecting the layer should open these details, while pointer selection of underlying points stays available. A line derived from a global population must stay visually and textually distinct from a facet-local line.

**Alternative.** A reusable external calculation object would support reuse in several charts, but it makes live bandwidth and facet-scope editing hard before a second consumer exists. A chart-local layer is the better first proof. Promote the result to a named reusable calculation only after a real second view needs identical inputs and parameters.

## 6. Scatter size, density, and relationship views

**Bubble encoding.** Extend `scatter`, not the registry. Let Size use a numeric field or fixed radius. Specify whether the input maps to radius or area; area is the honest default for a quantity comparison. Display a size legend, a minimum visible size, and an invalid-size count. Preserve point IDs and brush behavior. The point trace adds raw/prepared size, size-domain input, clamping, final radius, and overlap order. A bubble click still selects one row or uses the existing brush; size does not define a group. This is the smallest useful relationship addition.

**Binned density.** Add a scatter **Display** mode for rectangular X/Y bins before hexagons or contours. It answers overlap when too many points share pixels. Settings need X/Y bin counts or widths, metric initially count, and color domain. A bin trace includes both exact numeric intervals, input IDs, omitted-coordinate IDs, count, and color. A normal bin click can filter two numeric ranges; Inspect lists its rows. Keep the same domain rule as scatter so switching point/density mode does not move the analysis unexpectedly. Plot documents the two-dimensional bin-to-rectangle path ([Plot bin](https://observablehq.com/plot/transforms/bin)). A smooth density contour needs bandwidth and level semantics, and a contour encloses a weighted estimated region rather than an exact row subset. Its click should inspect the estimate, not claim exact membership.

**Correlation matrix.** Defer a new chart type until a task asks users to scan many field pairs. Its cell is a statistic over rows with valid values for *both* fields. It is not a region/channel subset, so clicking should open a scatter view of the pair and preserve current workspace filters. Settings would include selected numeric fields, coefficient method, missing-pair policy, and color domain. Trace a cell with valid pair IDs, omitted IDs, coefficient, sample count, and method. A matrix renderer alone does not supply this analysis.

**Scatterplot matrix.** Defer behind correlation-to-scatter. A bounded list of fields and a shared brush contract are the hard parts; rendering many small scatter plots without clear selection would add visual volume, not a direct answer.

## 7. Cumulative distributions and comparisons

**ECDF.** Add an `ecdf` chart type that shares numeric preparation with histogram and box plot. Its line and threshold action differ enough from bars and boxes to merit a clear saved type. It answers threshold and percentile questions: for each distinct valid value `x`, `F(x) = count(value <= x) / valid count`. Unlike a cumulative histogram, the ECDF is independent of bin width. Settings: numeric field, step direction, fraction/percent label, optional comparison scope. The x threshold action filters source values at or below that value; an Inspect action explains the count, valid denominator, missing exclusions, and exact IDs. Equal values share one step. No valid values yields an empty state. D3's cumulative and quantile utilities are available for calculation, while the source-ID map still belongs to explorEDA ([D3 summaries](https://d3js.org/d3-array/summarize)).

**Selected versus baseline.** First support one named baseline, such as “all rows before this selection,” for histogram and ECDF. The user must see both populations. A histogram comparison must share exact bin edges and say whether height is count or within-population percent. An ECDF comparison gives each population its own denominator on the same x domain. Baseline membership should be frozen at a clear action, not silently recomputed as the selection changes. Each mark trace identifies its population and IDs. This is a cross-chart selection feature; defer it until ordinary select/inspect/clear behavior is consistent.

## 8. Other proposed chart shapes

| Shape | Recommendation | Settings and trace condition that would justify it |
| --- | --- | --- |
| Pie or donut | Later preset of nonnegative category shares. | Metric, Top N, denominator, category IDs, and an accessible table. It adds little beyond bars for many categories. |
| Waterfall | Later, only for ordered contribution questions. | Explicit starting value, ordered deltas, subtotal rules, signed endpoints, and input IDs for each delta. |
| Calendar heatmap | Near-term new type over the daily time-series result. See the [focused research](calendar-map-sankey-parallel-research.md). | Day boundary and metric from the time-series result; a cell selects one day interval and traces exact rows. |
| Missingness matrix | Later diagnostic preset, after a real missing-data task. | Explicit row/field sampling or grouping; each cell names missing IDs and denominator. |
| Maps | Near-term Map type with Point and Region modes. The real dataset selects the first mode. See the [focused research](calendar-map-sankey-parallel-research.md). | Coordinate or region-join keys, unmatched rows, projection, source IDs; avoid automatic geocoding as a hidden setting. |
| Treemap or sunburst | Defer until nested categories matter. | Ordered hierarchy fields, additive metric, parent totals, drill path, and exact descendant IDs. |
| Sankey | Near-term stage-column view, with edge-list mode guided by real data. See the [focused research](calendar-map-sankey-parallel-research.md). | Stage identity, flow metric, missing-stage policy, node and link contributors. |
| Network | Separate future decision; arbitrary edges do not inherit Sankey flow semantics. | Node/edge identity, link records, cycles, and source membership. |
| Parallel coordinates | Near-term row-level view. See the [focused research](calendar-map-sankey-parallel-research.md). | Chosen axes and order, independent scales, stable categorical jitter, one polyline per source row, and brush intersection semantics. |
| Funnels, retention, Gantt | Domain work, not generic mark options. | Event order, cohorts and denominators, or start/end interval policy must be explicit before drawing. |

## Recommended order and decision gates

1. **Repair and expose what exists.** Complete grouped-bar select plus Inspect and trace, then add Histogram and Distribution presets and stable Other membership. This tests the shared action contract without a new renderer.
2. **Add a metric card.** It is a small second consumer of the same reducer and population rules. If its value differs from the bar or pivot on fixed rows, resolve that boundary before adding heatmap.
3. **Add categorical heatmap.** Use one exact cell and source inspection. Its two-key result tests whether the shared metric semantics scale without a general chart grammar.
4. **Add calendar rollup to Line.** Prioritize this before heatmap if real datasets more often ask time questions; its time-zone and missing-period choices need a fixed-data proof. Add a single area mode only after that result is stable.
5. **Add grouped/stacked bars, then ECDF and bubble size.** Each extends an existing family. Add comparison, density, and reference layers when a concrete analysis needs them. Keep correlation and unprioritized diagrams below the cut line.

One product judgment can reorder steps 3 and 4: are the next real datasets dominated by category-pair questions or by event timelines? Calendar heatmap, maps, Sankey, and parallel coordinates are also near-term priorities, with separate proof paths in the [focused research](calendar-map-sankey-parallel-research.md). Their order depends on the first real date, geographic, flow, and multivariate datasets. All early work can proceed without changing saved chart types or existing layouts.
