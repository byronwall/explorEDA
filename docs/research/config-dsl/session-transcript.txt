Recommendation: Outline

Use named clauses for common settings, indentation for detail, and an exact config block for native properties. This keeps field roles explicit without requiring YAML’s colons, list markers, or repeated object scaffolding.

The three alternatives express the same scatter chart:

Plain text
# Outline — explicit field roles
scatter x revenue y margin color category

# Phrase — controlled phrases, Y against X
scatter margin against revenue colored by category

# Slots — positional X, Y, optional color
scatter revenue margin category
Candidate	Main strength	Main weakness
Outline	Explicit roles make review, incremental edits, and diagnostic feedback straightforward.	Slightly more text for simple charts.
Phrase	Reads naturally and communicates relationships well.	Connective words become grammar; “Y against X” differs from the usual positional order.
Slots	Fewest characters for familiar chart signatures.	Readers and agents must remember positional meanings; optional arguments become harder to distinguish.

In the matched four-chart examples, Slots used 28% fewer header characters than Outline, but only 4% fewer characters overall once identical source mappings and detailed settings were included. That favors explicit roles over maximum compression for the canonical format.

The proposed everyday format
Plain text
source orders=salesRows
revenue:num=Revenue label="Revenue ($)"
margin:num=Margin
category:cat=Category

scatter x=revenue y=margin color=category
+ x.scale=symlog size=3 opacity=.55
hist revenue bins=24
row category
table revenue,margin,category

This removes the mandatory sources, fields, expect, and config scaffolding. There is no required indentation.

The main change is that several related settings fit naturally on one line. This is a complete 45-character chart declaration:

Plain text
scatter x=revenue y=margin size=3 opacity=.55
1. Inline pairs replace nested settings

Use key=value for common settings and exact native property paths for detailed settings:

Plain text
scatter x=revenue y=margin
+ margin.left=64 xAxis.grid=true xGridLines=6

No need to enter config, then margin, then left.

Common shorthand	Native setting
x=revenue	Resolve the field alias into xField.
size=3	pointSize=3
opacity=.55	pointOpacity=.55
x.scale=symlog	xAxis.scaleType=symlog

A few convenient names cover frequent settings. Everything else uses its native path rather than accumulating more special syntax.

2. Sources become one record per field
Plain text
revenue:num=Revenue label="Revenue ($)"
Part	Meaning
revenue	Short authoring name.
:num	Expected numeric type.
=Revenue	Exact field name in the supplied data.
label="Revenue ($)"	Display label.

The other short types are cat, date, and bool. Their full spellings are also accepted.

When the names already match, remove the repetition:

Plain text
source data
Revenue:num
Margin:num
Category:cat

With one declared source, use is unnecessary. With several sources, select one explicitly:

Plain text
use orders

The type suffix preserves the earlier distinction between checking a type and converting values. :num checks the expectation; coerce=num explicitly requests conversion. Neither a display label nor a type annotation silently changes field binding. 
REVIEW

3. Wrap only when it improves reading

A leading + continues the preceding declaration:

Plain text
scatter @margin x=revenue y=margin
+ color=category size=3 opacity=.55
+ margin.left=64 margin.right=24

Indentation is cosmetic. The + makes the continuation explicit without requiring a nested structure.

@margin gives the chart a stable ID. It is optional for sketches; agent-maintained documents should retain IDs so later edits have an unambiguous target.

The formatter offers 40-, 50-, 64-, and 80-character wrapping. It moves whole assignments, never splits a quoted value, and preserves comment-containing statements. A long title or literal JSON value can exceed the target—it is a wrapping preference, not a validity limit.

4. Omit role names only when they are redundant

For charts with one obvious input, these shorter forms are useful:

Plain text
hist revenue bins=24
row category
table revenue,margin,category

The explicit forms remain accepted:

Plain text
hist field=revenue bins=24
row field=category
table fields=revenue,margin,category

Scatter keeps x= and y=. Removing those saves little while making an accidental axis swap much harder to detect.

That is the compromise worth keeping: shorten an obvious single input, but do not turn multivariable charts into positional puzzles.

Detailed configuration remains available

Exact native objects and arrays remain the fallback for settings that do not deserve shorthand:

Plain text
scatter @margin
+ config={"xField":"Revenue","yField":"Margin"}
+ margin={"left":64,"right":24}

For example, a table column with an explicit ID and width:

Plain text
table @rows
+ columns=[{"id":"rev","field":"Revenue","width":180}]

These are checked configuration values, not a validation bypass. The production design retains this route to full native-setting coverage; the included prototype validates a limited chart subset.

One important boundary remains explicit: shorthand resolves aliases; exact native properties use native values. Thus x=revenue resolves the alias, while xField=Revenue supplies the raw native field name.

A simpler rule for conflicts

The earlier proposal had several override levels. This revision uses a simpler rule:

One explicit value per native property within a declaration.

This fails rather than silently choosing one value:

Plain text
scatter x=Revenue y=Margin size=3 pointSize=8

An intentional adjustment names its target:

Plain text
scatter @margin x=Revenue y=Margin size=3
edit margin size=8 margin.left=72

Likewise, a detached opacity=.5 line does not silently modify whichever chart precedes it. Use + nearby or edit margin elsewhere.

This costs a small amount of syntax but gives agents much safer feedback.

The final everyday format

This example defines source mappings, two calculations, five charts, and two chart-owned filters:

Plain text
eda 3 flat
source orders=salesRows
revenue:num=Revenue label="Revenue ($)"
cost:num=Cost
channel:cat=Channel

calc profit=revenue-cost
calc rate=revenue==0 ? null : profit/revenue
+ label="Margin" format=percent precision=1

scatter @profit x=revenue y=profit
+ color=channel size=3 where.profit=0..
row @channels channel where.channel=Web,Store
hist @distribution profit bins=24
metric @total sum=profit
table @records revenue,profit,rate,channel

14 nonblank lines. Longest line: 45 characters. No indentation.

The source section and version header are optional. Stable IDs are optional for sketches but recommended for agent-maintained documents.

1. Calculations look like calculations

A calculation is a named expression, available to subsequent—or earlier—chart declarations:

Plain text
calc profit=revenue-cost
calc segment=profit<0 ? "Loss" : "Profit"
scatter x=revenue y=profit color=segment

There is no calculations block, quoted formula wrapper, or repeated resultColumnName property. Optional display metadata stays separate from the expression:

Plain text
calc profit=revenue-cost
+ label="Profit ($)" format=currency currency=USD

The checker resolves dependencies, accepts forward references, rejects cycles and name collisions, and emits native calculation definitions in dependency order. This targets explorEDA’s existing formula-text representation and calculation model rather than introducing an unrelated expression engine.

Aliases are resolved structurally. A field reference to revenue becomes a reference to Revenue; the literal string "revenue" stays unchanged. Unusual native field names use the existing bracket form:

Plain text
calc profit=["Net revenue"]-["Total cost"]
Row calculations and chart aggregates stay distinct
Plain text
calc average=avg(revenue,cost)
metric @total sum=profit
metric @average avg=profit
metric @orders count

The first line averages two values within each row. The other lines aggregate the chart’s applicable rows. In the inspected calculation registry, sum, avg, and count operate on supplied arguments—not implicitly across the dataset. The checker warns about obvious mistakes such as using calc total=sum(revenue) to request a dataset total.

2. Filters remain ordinary key-value pairs

Rather than introducing a trailing SQL-like clause, filters use the same assignment structure as other settings:

Plain text
scatter x=revenue y=profit where.profit=0..

The field is in the key; the selection is in the value.

Filter pair	Meaning
where.profit=0..	At least zero.
where.revenue=100..500	Inclusive range.
where.revenue=..500	At most 500.
where.channel=Web,Store	Either category.
where.channel="Web,Store"	One literal category containing a comma.
where.returned=false	Boolean false.
where.cost=null	Native missing-value selection.
where.product.contains=Pro	Case-insensitive text containment.

These forms lower to the existing range, value, and text filter structures. Numeric range endpoints are inclusive; missing-value and text matching preserve the native engine’s semantics.

Several filters still fit comfortably on short lines:

Plain text
metric @orders count where.channel=Web,Store
+ where.revenue=100..500 where.returned=false

Different fields combine with AND. Values inside a list combine with OR.

Date ranges use the same shape:

Plain text
+ where.date=2026-10-01..2026-10-31

The checker requires a datetime field and validates the bounds. A date-only upper bound includes that whole UTC day, matching the inspected filter implementation.

Complex conditions become explicit calculated fields

Strict comparisons and cross-field OR do not need another query grammar:

Plain text
calc keep=revenue>100 || channel=="Web"
table @selected revenue,channel,keep
+ where.keep=true

The predicate is a visible, reusable calculation—not a hidden generated field. Including keep in the table is deliberate: the pinned table implementation applies filters to fields included in its columns.

“Per chart” means ownership, not a private dataset

The chart owns its filter, but that filter participates in explorEDA’s linked workspace filtering. A scatter can retain dimmed context points outside its own selection; drawn points and rows passing all filters are therefore different populations. Clearing one chart’s filter does not clear another chart’s selection. 
REVIEW

The checker checks this behavior, not merely whether a filter object has valid keys. A filter that the pinned chart would ignore—or display inconsistently—produces an error rather than a misleading success.

3. Safe edits are compact too

IDs make later changes precise:

Plain text
scatter @p x=revenue y=profit size=3
+ where.profit=0..

edit p size=4 where.profit=100..500

Editing a field filter replaces that field’s constraint while retaining the chart’s other filters.

Edit	Effect
edit p where.profit=*	Remove this chart’s filter on profit.
edit p where=none	Remove all filters owned by this chart.
edit p where.profit=[]	Select no values; not a clear action.

An unquoted * is a removal operation only in an edit. Quoted "*" remains literal text. null never means “delete this setting.”

Contradictory assignments and competing edits fail rather than relying on silent last-writer-wins behavior. Calculations are changed through their original declarations, not through a second calculation-edit language.

4. Detailed settings still have a direct route

Common properties get shorthand; uncommon properties keep their native names:

Plain text
scatter @p x=revenue y=profit
+ size=3 opacity=.55 x.scale=symlog
+ margin.left=64 xAxis.grid=true xGridLines=6

Literal native JSON handles arrays and uncommon object structures:

Plain text
table @rows
+ columns=[{"id":"r","field":"Revenue","width":180}]

There is no mandatory config wrapper. Exact native properties use exact native field names; shorthand resolves authoring aliases. This preserves the distinction established in the previous review. 
REVIEW

The final design retains a native-configuration route for settings without shorthand. The executable checker validates a defined subset; it does not pretend to implement every native chart schema.

The updated checker returns locations, suggestions, resolved calculation dependencies, native-name chart patches, and filter ownership. Errors distinguish a malformed expression from an unknown field, a dependency cycle, an impossible range, or an ineffective chart filter.

For automated repairs, the CLI supplies a SHA-256 document digest. A repair must match that digest and the expected text at each source range. Overlapping edits and stale input fail before any write.
