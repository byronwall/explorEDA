Annotations in front-end data visualization
Library survey, editing capabilities, and a reusable system design

Research date: October 1, 2026

The central finding is that annotation rendering, annotation editing, and durable semantic anchoring are three different capabilities. Most visualization libraries provide the first. Some provide draggable objects or editing handles. A smaller group provides an actual authoring interface. None of those facts, by itself, establishes that an annotation will remain attached to the correct observation after filtering, data replacement, or changes to chart structure.

For a product that needs built-in editing, the strongest approaches inspected here are AG Charts annotations, Highcharts with the appropriate annotation/Stock Tools modules, ApexCharts Ink plus Rewind, and amCharts Stock drawing tools. Their coverage and licensing differ substantially. Plotly.js occupies a useful middle ground: native annotation editing and shape drawing, but not a complete annotation-management product. D3, Vega, visx, and general drawing editors are stronger foundations when application-specific semantics and interaction design matter more than minimizing implementation work.

1. What an annotation system actually needs to represent

Research on annotation design treats annotations as more than text placed over a chart. ChartAccent investigated data-driven annotation authoring using a corpus of 106 charts from six newsrooms. More recent qualitative research emphasizes audience, purpose, visual salience, and how annotations survive changes in presentation medium. These are useful design guides, but not evidence that adding more annotations invariably improves comprehension.

A useful working taxonomy separates the subject being annotated, the visual form, and the intended meaning:

Type	Typical subject and representation	Important modeling decision
Label	A datum, series, category, or location; text near its subject	Is the text a live field value, a formatted expression, or authored prose?
Callout	A subject plus a displaced note and connector	Keep the subject anchor separate from the note’s placement.
Arrow / connector	A relationship between two positions, or a note pointing to a subject	Distinguish two data-space endpoints from a data anchor plus a pixel offset.
Reference line	A threshold, target, date, baseline, or statistical result	A constant value and a dynamically computed statistic are different anchors.
Reference band	An interval along one axis, often spanning the other axis	Distinguish a visual band from an analytical interval with inclusive/exclusive boundaries.
Range / bracket	An interval, duration, comparison, or measured span	Store endpoint semantics and units, not just a rectangle’s dimensions.
Highlighted region	Selected records, a geometric region, or an exceptional area	“These records” should not be confused with “whatever lies inside this box.”
Shape	Rectangle, ellipse, polygon, path, or enclosure	Decide which dimensions are data-scaled and which are fixed visual sizes.
Event marker	A timestamp/category and an event description	An event may belong to an independent dataset rather than a plotted series.
Image / icon	A data point, plot region, or view-level location	Separate asset identity, alternative text, intrinsic dimensions, and placement.
Freehand drawing	A gesture over a view or over data coordinates	Choose explicitly whether the stroke follows data, plot proportions, or screen pixels.

Several distinctions prevent misleading feature comparisons:

A tooltip is not automatically a persistent annotation.
A brush or lasso selection is not an annotation until its result is promoted into a durable object.
A click callback is not a selection model.
A draggable option is not an authoring toolbar, text editor, history system, or persistence layer.
A hand-drawn appearance is not freehand input. Rough Notation, for example, creates sketch-like emphasis around DOM elements; it is not a drawing editor.

5. Deeper case studies

The examples below illustrate integration boundaries. Helpers such as store.commitPosition, adapter.consumeRelayout, and saveState are application code, not vendor APIs.

5.1 Plotly.js: strong mixed coordinates and useful native editing

Plotly’s structure cleanly separates text annotations from geometric shapes. This supports a common combination: a callout attached to a data value and a highlighted interval spanning the plotting height.

JavaScript
const layout = {
  annotations: [{
    x: 12, y: 80,
    xref: "x", yref: "y",
    ax: 48, ay: -36,
    axref: "pixel", ayref: "pixel",
    text: "Launch effect",
    showarrow: true
  }],
  shapes: [{
    type: "rect",
    xref: "x", yref: "paper",
    x0: 10, x1: 14,
    y0: 0, y1: 1,
    opacity: 0.2
  }]
};

const config = {
  edits: {
    annotationPosition: true,
    annotationTail: true,
    annotationText: true,
    shapePosition: true
  },
  modeBarButtonsToAdd: [
    "drawline", "drawopenpath", "drawrect", "eraseshape"
  ]
};

Here the callout subject follows the axes, while its tail remains offset in pixels. For an absolute axis-coordinate tail, axref must exactly match xref, and likewise for ayref/yref; otherwise the reference falls back to pixel behavior. Plot-normalized paper positioning and axis-domain fractions are different scopes. 
Plotly

Prefer granular edits flags to indiscriminately enabling editable, which can enable editing beyond annotations. Drawing modes cover geometric creation; they do not constitute a full text/image authoring palette or style inspector.

+1

5.2 AG Charts: the most complete general Cartesian editor inspected

The current Enterprise annotation documentation is not limited to financial charts. It exposes a Cartesian subset of text, comments, callouts, notes, lines, arrows, and certain channels, with toolbar/settings interactions and keyboard operations including deletion, copy/paste, nudging, and undo/redo. Financial chart tooling has a broader vocabulary. 
AG Grid

After registering the appropriate modules, a state-oriented integration can look like:

JavaScript
let chart;

chart = AgCharts.create({
  ...baseOptions,
  annotations: { enabled: true },
  initialState: {
    annotations: [{
      type: "comment",
      x: { value: "Jun", groupPercentage: 0.15 },
      y: 92,
      text: "Campaign result"
    }]
  },
  listeners: {
    annotations: () => {
      if (chart) saveState(chart.getState());
    }
  }
});

The annotation-change listener is listeners.annotations. The state APIs are getState, setState, and initialState; these are preferable to scraping drawn objects. Category positions can include an intra-group fraction, and serialized date state has an explicit representation. Preserve the returned state version rather than pretending it is the same thing as your annotation schema version.

+1

Tradeoff: this reduces editor implementation substantially, but creates an Enterprise dependency and a vendor-specific state contract. I would wrap it with semantic IDs and migration logic rather than expose raw chart state as the sole long-term document format.

7. Coordinate semantics and lifecycle behavior
Data-bound is not necessarily record-bound

These three annotations can initially look identical:

“Place a callout at x = September 14, y = 128,000.”
“Place a callout on record O-1042, using its date and revenue fields.”
“Place a callout on the maximum revenue record in the current filter.”

They have different update semantics.

The first follows a coordinate. The second follows a stable record. The third follows a versioned query. A reusable system should not convert all three into an {x, y} pair and discard the distinction.

Recommended behavior contract

The following is a proposed product policy, not a claim that every library implements it.

Change	Data-value anchor	Datum/query anchor	Pixel/normalized geometry
Zoom / pan	Reproject through current scales; preserve the value.	Resolve the subject, then reproject.	View pixels remain fixed; plot fractions follow plot bounds.
Resize / responsive layout	Reproject using new plot dimensions.	Resolve and reproject; rerun label layout if allowed.	CSS-pixel offsets stay visually fixed; normalized positions scale with the relevant plot.
Filtering	Usually remains meaningful even if associated series disappear.	Distinguish filtered-out from deleted. Queries must declare whether they use filtered or full data.	A screen box remains a screen box; it must not silently become a selection of new records.
Data refresh	Value remains constant unless explicitly edited.	Stable row keys follow changed field values; query anchors recompute under declared semantics.	No semantic update unless explicitly bound.
Axis change	Validate units, scale type, domain, and axis identity.	Re-resolve field-to-axis bindings.	Preserve intended visual placement, but invalidate assumptions tied to the old plot.
Facet/panel reorder	Resolve semantic facet key to its current panel.	Same; never use panel order as the only identity.	Recompute local-to-view transforms.
Export	Reproject against the export’s logical viewport.	Resolve against the intended data revision/filter.	Define CSS-pixel-to-export scaling explicitly; do not accidentally apply device-pixel ratio twice.

Several rules follow.

Use semantic axis IDs. An application-level revenue-usd axis should map to the vendor’s current y2, index 1, or scale object. Persisting the vendor’s array index alone is fragile.

Keep coordinate spaces explicit per dimension. A horizontal threshold can use an axis value for y and plot fractions for its horizontal extent. A callout can use a datum subject and CSS-pixel note offset. Plotly supports analogous mixed references natively; Highcharts also distinguishes point/axis/pixel attachment. 
Plotly
+1

Treat categorical inversion specially. A category and an intra-band position are not the same as a continuous number. AG Charts’ group-percentage representation is a useful example of making this explicit. 
AG Grid

Dragging a datum-bound subject needs an explicit meaning. It should either reattach to another record, detach into a coordinate anchor, or be prohibited. It should not silently modify the underlying measurement merely because a pointer moved.

Freehand is not always transformable by one matrix. A data-bound stroke over logarithmic or other nonlinear axes must be reprojected sample by sample. A normalized review scribble has different semantics and should remain normalized.

Automatic label layout is derived state. Keep authored offsets and layout constraints separately from the latest collision-avoidance result. Otherwise every resize can look like an authored edit.

8.2 Anchor types

The attached model has four principal anchor variants:

Anchor	Meaning	Example
Coordinate	A literal location with explicit coordinate space per dimension	x is a timestamp on time; y is 0.1 of plot height
Datum	A stable row key plus field/axis bindings	sales, key {orderId:"O-1042"}, x=completedAt, y=revenueUsd
Row set	A named collection of stable records	Enclose the selected accounts even after sorting
Derived	An allowlisted, versioned resolver with parameters and input scope	“Maximum revenue in filter F,” rather than arbitrary JavaScript in JSON

For coordinate anchors, each dimension is an explicit union:

TypeScript
type Coordinate =
  | {
      space: "axis";
      axisId: Id;
      value: Scalar;
      bandPosition?: number;
    }
  | { space: "plot-fraction"; value: number }
  | { space: "view-css-px"; value: number };

The model defines plot fractions and view pixels with a top-left origin, y increasing downward. Vendor adapters must convert different conventions, including Plotly’s bottom-origin normalized y positioning.

8.4 Geometry, content, and assets

Geometry is a discriminated union for labels, callouts, markers/events, lines/arrows, rules, bands, shapes, polygons, highlights, images, and freehand strokes. It references anchors rather than duplicating data identity.

Content is plain text, a restricted rich-text structure, or an asset reference. Avoid arbitrary HTML, executable formatting functions, DOM elements, canvas objects, and class instances in the persistent document.

Images should reference an application asset-store key, with media type, dimensions, and optionally a content hash. Temporary signed URLs are delivery mechanisms, not durable asset identity.

For freehand, persist the chosen frame—continuous axes, plot fractions, or view pixels—along with samples and optional pressure/timing. Large strokes may need separate assets or bounded/chunked storage.

The proposed v1 is intentionally oriented around Cartesian views. Geographic, polar, and 3D anchoring should receive explicit versioned projection extensions rather than being disguised as ordinary screen coordinates.

9. Recommended reusable architecture
9.1 Own the semantic document; adapt the renderer

Use this pipeline:

Semantic document → anchor resolution → coordinate projection → label/shape layout → rendering and hit testing

The editor then sends semantic commands back to the document.

An adapter needs, at minimum, the ability to resolve anchors, project coordinates, and invert pointer positions. A production adapter should additionally expose capabilities, hit testing, snapping candidates, view/facet bounds, export behavior, and supported geometry.

The attached interface includes:

TypeScript
interface ChartAdapter {
  id: string;
  version: string;

  resolve(anchor: Anchor): AnchorResolution;

  project(
    scope: Scope,
    x: Coordinate,
    y: Coordinate
  ): CssPoint;

  unproject(
    scope: Scope,
    point: CssPoint,
    axes: { x: Id; y: Id }
  ): {
    x: Scalar;
    y: Scalar;
    xBandPosition?: number;
    yBandPosition?: number;
  };
}

Avoid renderer internals as the canonical model. Plotly’s array patches, amCharts’ panel indices, Chart.js rendered elements, React component instances, and drawing-editor scene objects are integration details. Normalize them at the boundary.

9.2 Transient state stays transient

Selection, hover, focus, current tool, pointer capture, drag previews, snap guides, and auto-layout caches should not be serialized into the annotation document.

Keep separate state for:

The authored annotation document.
The editor session.
The chart viewport/filter state.
Collaboration presence.

A collaborator selecting a note should not produce a permanent document revision.

9.3 Edit lifecycle and history

Use four lifecycle phases:

TypeScript
type EditorEvent =
  | { phase: "begin"; gestureId: Id; annotationIds: Id[] }
  | { phase: "preview"; gestureId: Id; annotations: Annotation[] }
  | { phase: "commit"; gestureId?: Id; transaction: EditTransaction }
  | { phase: "cancel"; gestureId: Id };

Pointer movement updates a preview. Pointer release commits one transaction. Escape restores the pre-gesture state. Text edits should have a similarly deliberate commit/coalescing policy.

Commands should address stable IDs:

add / remove
set-anchor
set-geometry
set-content
set-style

Do not expose vendor paths such as annotations[4].x as the durable operation format.

For undo, record inverses or before/after values for the changed components. A label drag should undo its offset change, not restore an old whole-document snapshot that also erases someone else’s text edit.

Choose one history authority. Native history plus an unrelated application history can produce double undo, missing edits, or divergent states. Either delegate and normalize its transactions, or disable/bypass it in favor of application-owned history.

9.4 Snapping

Treat snapping as a policy with distinct candidate classes:

Data-record snapping, tick/grid snapping, geometric alignment, and angle constraints are not interchangeable.

Measure tolerance in CSS pixels so interaction remains usable at different zoom levels, then commit the corresponding semantic result. A snap to a record can create a datum anchor; a snap to a gridline usually creates a coordinate anchor.

Expose both a toggle and a temporary modifier override. Do not promise record snapping merely because a vendor option is named snap.

9.5 Storage, serialization, and migrations

A practical storage design is a canonical snapshot plus an optional operation log. Track separately:

Schema version, document revision, dataset revision, and adapter/library version.

Use optimistic concurrency or another explicit revision protocol, idempotent transaction IDs, and server-side authorization. A client-side locked flag is only a UI affordance.

At the serialization boundary:

Reject non-finite numbers and unsupported object types.
Canonicalize timestamps and distinguish instants from local calendar dates.
Validate IDs, anchor references, axis compatibility, and geometry cardinality.
Allowlist derived resolvers and sanitize content/assets.
Bound text length, path sizes, nesting, and total payload size.
Preserve namespaced extensions, but reject unsupported major schema versions.

Migrations should be pure, versioned, and tested against old documents. Do not silently discard unknown annotation kinds during a round trip.

9.6 Orphaned and temporarily unresolved anchors

Distinguish at least:

Filtered out, offscreen, deleted, source unavailable, invalid value, missing axis, and missing facet.

These are not interchangeable failures.

A stored snapshot can support a visibly stale “ghost” annotation or a repair UI. It must not silently become a new authoritative anchor. Never reattach a deleted record to the nearest point without an explicit user action.

A useful repair interface offers “reattach to record,” “convert to fixed coordinate,” and “remove,” while preserving provenance.

9.7 Collaboration

Use a map keyed by annotation ID rather than treating the entire annotation array as one last-writer-wins value.

Merge independent fields where appropriate, but treat a semantic anchor tuple—dataset, row key, field bindings, axis IDs—as an atomic unit unless the product has a well-defined finer-grained conflict model. Text may deserve its own CRDT; geometry usually needs different semantics.

Deletion needs tombstone/conflict handling. Presence, cursor locations, and in-progress gestures belong in an ephemeral channel.

Yjs’ UndoManager supports tracked origins and capture boundaries, which can help implement actor-local undo. It does not decide what a chart anchor means or resolve incompatible simultaneous reattachments for you. 
Yjs Documentation

9.8 Accessibility

Accessible chart output is not the same as an accessible annotation editor.

Provide a DOM annotation list with meaningful reading order, selectable items, text/coordinate forms, and clear actions. Support keyboard creation, navigation, movement, resizing, deletion, undo/redo, and cancellation. Restore focus after deletion or closing an inspector.

Also provide a non-drag single-pointer alternative where dragging is not essential—for example, selecting a note and entering its position in a form. Keyboard support alone does not satisfy WCAG 2.2’s dragging-movements requirement. 
W3C

Describe the meaning of a highlight or freehand enclosure, not merely its path coordinates. Do not rely on color alone for selection or annotation meaning. Announce unresolved anchors, completed edits, and validation errors without narrating every pointer movement.

tldraw’s documented accessibility features and AG Charts’ documented keyboard operations are useful starting points, not substitutes for testing the integrated product. 
tldraw
+1

9.9 Export is a separate rendering target

Rehydrate the semantic document against the export viewport and intended data revision. Exclude handles, selection outlines, snap guides, and editor popups.

An external overlay will not become part of a vendor’s export merely because it visually overlaps the chart. Implement an explicit composition/export path.

Test images, fonts, clipping, rich text, SVG foreign content, canvas layers, and device-pixel ratios. When reproducibility or later editing matters, export the annotation JSON as a sidecar rather than relying only on pixels or SVG paths.
