## 4. Retention follow-through and stable recommendation IDs

The six IDs below are the complete recommendation set for this research. They do not add implementation milestones automatically.

### RO01 — Retain the snapshot contract now

Keep period-specific activity, current entry semantics, trace, and entity selection. Distinguish a zero count in recorded rows from an assertion of complete observation. Reconsider if executed behavior contradicts the explicit contract or a consequential real interpretation failure survives the existing explanation. Do not require an invented number of customers before examining a clear failure.

### RO02 — Local trust, then the bounded retention proof

After the local trust task, run the fixture in [proof-plan.md](proof-plan.md). Include the quiet-complete versus missing-collection pair with identical event rows, an unrelated late event, removed entry rows, chart-local versus facet scope, UTC boundaries, and All-row arithmetic. Record source predictions separately from observed outputs. If the fixture disagrees with the runtime, reconcile that disagreement before evaluating a product change. Browser and author checks remain unrun here.

### RO03 — One conditional lesson and runnable example together

Only an observed misunderstanding earns the proposed **“Read the observation window”** section in `apps/demo/src/docs/pages/retention.mdx`, paired in the same milestone with proposed `apps/demo/src/demos/retentionObservation.ts`. Neither is created by these reports. The example should be runnable through the existing demo conventions and support checking source rows, selected entities, and denominators.

Test whether the short explanation resolves the actual error. Defer it if current trace and docs already suffice, or if the supposed misunderstanding is an unavailable coverage fact. Keep the lesson proportional; duplicating implementation detail across another guide creates upkeep without establishing observation. Pairing docs and example follows the repository's planning rule. [AGENTS.md](https://github.com/byronwall/explorEDA/blob/9b16d78e3ed0742ed4d5858c1939fec9e758b510/AGENTS.md); [current retention docs](https://github.com/byronwall/explorEDA/blob/9b16d78e3ed0742ed4d5858c1939fec9e758b510/apps/demo/src/docs/pages/retention.mdx).

### RO04 — Compare upstream authored facts when they exist

For a task requiring trustworthy coverage, compare an authored cohort/observation table with existing event controls. Declare the grain, denominator membership, provenance, and inspection path. A summarized table can weaken event/entity lineage; a detailed table can increase author work. Measure that tradeoff rather than assuming upstream preparation is free. This is a candidate, not a compulsory hurdle before a smaller chart input may be considered.

### RO05 — Defer one explicit observation endpoint

A named, consequential task must supply more than its latest event timestamp. Obtain the asserted interval, applicable entities and event types, common or differing facet/cohort scope, timezone, endpoint convention, and basis for believing collection covered the interval. Separate an analysis cutoff from a claim of collection completeness. Name the unresolved choice of whether the endpoint truncates activity, changes eligibility, or both.

If all relevant cohorts and entities share one trustworthy interval, compare one endpoint with the smallest relevant alternative. If coverage varies or contains interior gaps, a single endpoint fails that task. Do not expand it into a coverage engine. Controls, a lesson, and upstream preparation need not fail in a prescribed sequence; compare what the observed task actually needs.

### RO06 — Evaluate completed-only All independently

Compare the present reached-cohort pool with a completed-only pool while keeping displayed cohort cells and selection semantics explicit. Show which cohorts are omitted, how the denominator changes, and what happens when none qualify. Excluding partial periods changes the summary question and does not establish collection completeness. A documented comparator option is evidence of a possible contract, not evidence that explorEDA's current choice is defective. The first arithmetic comparison excludes cells carrying the current partial flag; that is not yet exact completed-calendar eligibility, because the flag rounds through the last event's UTC date. Any stricter maturity rule is a separate product choice.
