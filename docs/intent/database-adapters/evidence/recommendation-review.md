# Database adapter recommendation review

This review reconciles every `DBA-001` through `DBA-016` proposal in the preserved Pro packet with the current request, checkout, and independently checked primary documentation. `Adopt` records the selected shape. `Investigate` marks a falsifiable later choice. `Defer` keeps work below the first proof. `Reject` rules out the proposed behavior under the current contract.

## Decisions

| ID | Disposition | Evidence and uncertainty |
| --- | --- | --- |
| DBA-001 | adopt | `ExplorEdaProjectProps.tables` takes source arrays, and `ExplorEdaProject` calls the local `useAnalysisEvaluation` path. This is a real integration seam. Complete snapshots still may exceed an agreed workload budget. |
| DBA-002 | adopt | Start with PostgreSQL through host-owned `pg` code. node-postgres documents bound values and says transactions require one checked-out client; PostgreSQL repeatable-read provides one snapshot across statements. A local fixture does not prove customer network access, TLS setup, or the final runtime. ([queries](https://node-postgres.com/features/queries), [transactions](https://node-postgres.com/features/transactions), [pool API](https://node-postgres.com/apis/pool), [PostgreSQL isolation](https://www.postgresql.org/docs/18/transaction-iso.html)) |
| DBA-003 | investigate | A second driver earns work only if the PostgreSQL proof shows that a reusable boundary would help and a distinct runtime or type model can test it. SQLite is a candidate because Node documents `DatabaseSync` as synchronous and the API as release-candidate status in current docs. Exact runtime/version and process containment remain open. ([Node 24 SQLite docs](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html)) |
| DBA-004 | adopt | The local evaluator has source, lookup, expand, calculate, filter, and aggregate steps. The supplied repository review identifies different analysis and workspace aggregation/filter meanings. Keep those contexts separate and reject unproven server plans. Exact edge behavior needs oracle tests before pushdown. |
| DBA-005 | adopt | Admit only declared values that preserve meaning through current field settings and parsing. The report identifies int64, exact decimal, submillisecond dates, booleans, and complex values as loss risks. First-release supported types and precision ranges need fixture proof. |
| DBA-006 | adopt | Keep database keys separate from generated local `__ID` values. Stable keys must survive sorting and refresh; rows without keys can receive snapshot-only occurrence identity. Composite encoding and selection behavior require direct tests. |
| DBA-007 | adopt | The first reader publishes all registered sources atomically or fails. Every source must share one consistent database snapshot and report field/row coverage, counts, and snapshot identity. A client envelope cannot detect every self-consistent false-completeness claim; the trusted reader and oracle fixtures must prove exhaustion. |
| DBA-008 | adopt | Use host-owned fixed reads and a small complete-or-error result contract. Keep authorization, SQL, and driver objects on the host. Do not create a reusable package or broad capability matrix before a second driver demonstrates common needs. |
| DBA-009 | adopt | Source IDs resolve through server-owned definitions; bind values and restrict read permissions. Enforce independent query, cell, byte, and time bounds before uncontrolled buffering. Driver and host controls do not by themselves bound scans or expansion. |
| DBA-010 | investigate | Stale results must not publish, and engine cleanup must be observed before a resource is reused. node-postgres exposes client destruction; this does not establish confirmed query cancellation. Node `DatabaseSync` runs synchronously, so a child process may be required. The pinned-driver cleanup mechanism and observation bound need proof before promising stop behavior. ([pool API](https://node-postgres.com/apis/pool), [Node 24 SQLite docs](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html)) |
| DBA-011 | defer | Evaluate one typed row or aggregate operation only after the complete-snapshot baseline. Promote it only when local-oracle parity holds for nulls, identity, joins, row grain, contributors, and empty inputs, and a named workload improves. SQL syntax similarity is not parity evidence. |
| DBA-012 | defer | Cross-database federation and arbitrary server formulas add policy, snapshot, type, and lineage problems. Revisit only for a named customer demand with its own proof. |
| DBA-013 | defer | DuckDB as the default, a separate query service, and a universal adapter platform do not help the first visible PostgreSQL path. A file-analytics or private-network requirement may change that decision. |
| DBA-014 | reject | Partial rows cannot be labeled exact or complete, and aggregate rows cannot be wrapped as a full `AnalysisEvaluation`. The current evaluator exposes stages and source/contributor evidence. Partial and aggregate-only support needs a separate honest consumer contract. |
| DBA-015 | adopt | Use a deterministic fake for fast semantic checks and a disposable PostgreSQL fixture for driver behavior, with intentional failures. Measure only a named workload. Keep the current local path usable. No application tests or benchmarks have run in this shaping work. |
| DBA-016 | defer | Per-customer instances and high automation are explicit. This initiative supplies runtime, network, transaction, resource, secret, and file/process constraints; hosting chooses the platform. Customer connectivity and lifecycle automation remain unproven. |

## Direct checks and limits

The current checkout is `28c5ac27a400aa1fd66ce99eb1e6bd4ab5c72e9c`, which differs from the Pro packet’s declared source snapshot. Direct inspection confirmed the `tables` prop, local evaluator call, and six step kinds in the current files. This validates the proposed seam in this checkout; it does not validate runtime behavior or the packet’s claims about omitted source files.

Primary documentation independently confirmed parameter binding and the identifier boundary in node-postgres, transaction affinity to one client, the repeatable-read snapshot behavior in PostgreSQL, and the synchronous API/release status of Node SQLite. Documentation does not prove the proposed driver versions, actual database contents, stop timing, hosting compatibility, or customer connectivity. Those claims remain first-proof work.
