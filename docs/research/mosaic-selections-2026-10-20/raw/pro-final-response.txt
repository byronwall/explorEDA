Findings that most affect the next implementation
1. Histogram boundaries can disagree with linked evidence

The source partitions an internal numeric bin as half-open, while the emitted range is evaluated inclusively.

For values 0, 0.5, and 1 in two bins:

The first displayed bin is [0, 0.5) and contains only 0.
Its emitted filter can be { min: 0, max: 0.5 }.
The common evaluator accepts 0.5, adding a record that belongs to the adjacent bin.

The same pattern appears in Scatter marginals. This is a concrete static counterexample, not a runtime reproduction. The recommended fix is explicit interval closure, preserving the inclusive meaning of existing saved ranges—not subtracting an arbitrary floating-point epsilon. Sources: 
histogram plan, 
selection writer, and 
filter evaluator.

2. Source-chart context must be distinguished from selected evidence

A source histogram may intentionally show records passing other charts’ selections while excluding its own selection from its context distribution. Its selected overlay, table, export, and written count can still use the full intersection.

The proposed contract therefore distinguishes:

Population restrictions, including workspace, chart-local, and facet scope.
Interactive predicates and their originating chart.
Source-chart context versus exact selected evidence.
Highlighting, viewport changes, and encoding domains.

Two charts selecting the same field must remain separate owners. Clearing one must preserve the other. This extends the existing 
Crossfilter resolution behavior, rather than replacing it with a field-keyed global selection.

3. Hiding a filtered table column can create a scope discrepancy

The dashboard table’s local evaluator continues applying saved filters, while its linked definition looks up fields through the configured columns. Removing a filtered column from that list can therefore leave the table and its siblings using different predicates.

The recommended policy is to retain the filter with a visible indication; explicitly clearing it on hide is another defensible choice. The implementation should not choose implicitly through presentation state. This is also a source-derived candidate requiring reproduction. Sources: 
table definition, 
local row filtering, and 
column operations.

4. Persistence needs deliberate extension

Existing project row-key adaptation is valuable and should be reused. It currently traverses particular chart and Rows filter locations; a new polygon, workspace/local filter location, or binding does not automatically inherit that handling.

The report also identifies typed-value risks in dashboard text: numeric 1 and string "1" can collide through string-based lookup. Export paths have different fallback guarantees. A richer selection must either round-trip exactly or be explicitly rejected by an unsupported export path. Sources: 
logical row-key adapter,

Performance conclusions

Metadata alone will not bring Mosaic’s optimizer to Crossfilter. The inspected optimizer works through structured queries, compatible grouping and selection dimensions, sufficient aggregate measures, and a supporting query backend. Its benefits must be weighed against materialization, memory, active-source switching, invalidation, and exact evidence retrieval. The report grounds this in the pinned 
pre-aggregation implementation.

The study separately addresses two correctness risks:

Aggregation can be exact for quantized bins while admitting records outside the intended source-space interval.
Support for union selection semantics does not by itself prove compatibility with an optimization derived around prefiltering by other clauses.

Both are treated as static concerns requiring targeted parity tests, not reproduced upstream failures.

The benchmark analysis distinguishes query-group completion from interaction-to-paint latency, separates loading and materialization from updates, explains favorable prefetch lead time, and records unresolved paper/harness cardinality discrepancies.
